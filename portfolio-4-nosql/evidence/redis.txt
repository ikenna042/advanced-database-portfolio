=== R1  Idempotency: 20 copies of one request arrive at the same moment ===
Each copy runs: SET idem:<customer>:<key> processing NX EX 86400
NX means 'only if the key does not exist', so exactly one copy can claim it.
Copies that got OK (and would go on to post the transfer): 1
Copies that got nil (and would wait for the stored result): 19
The winner stores the result, keeping the 24-hour expiry (KEEPTTL):
OK
{"status":"completed"}
Seconds until Redis forgets the key: 86399
PostgreSQL's idempotency_keys table stays the durable record; Redis is the fast first check.

=== R2  Rate limiting PIN attempts: at most 5 in any 60 seconds ===
Fixed window with INCR + EXPIRE, the simplest version:
  attempt 1: count 1, allowed
  attempt 2: count 2, allowed
  attempt 3: count 3, allowed
  attempt 4: count 4, allowed
  attempt 5: count 5, allowed
  attempt 6: count 6, BLOCKED
  attempt 7: count 7, BLOCKED
A fixed window resets on the minute, so 5 attempts at 09:15:59 and 5 more at 09:16:00 all pass.
Sliding window with a sorted set, in one atomic Lua script (sliding_window.lua):
  attempt at +0s: allowed (attempts in the last 60 s: 1)
  attempt at +5s: allowed (attempts in the last 60 s: 2)
  attempt at +10s: allowed (attempts in the last 60 s: 3)
  attempt at +15s: allowed (attempts in the last 60 s: 4)
  attempt at +20s: allowed (attempts in the last 60 s: 5)
  attempt at +25s: BLOCKED (attempts in the last 60 s: 5)
  attempt at +30s: BLOCKED (attempts in the last 60 s: 5)
  attempt at +61s: allowed (attempts in the last 60 s: 5)
  attempt at +62s: BLOCKED (attempts in the last 60 s: 5)
At +61s the attempts from +0s left the window, so one more was allowed.

=== R4  Cache-aside for wallet balances, and why the cache must be invalidated ===
1. App asks Redis first: GET bal:1100000001 -> '' (a miss)
2. App reads PostgreSQL (28776510 kobo) and caches it for 30 seconds.
3. Next read is a hit: GET bal:1100000001 -> 28776510
4. A N1,000 transfer commits in PostgreSQL. Balance there is now 28676510.
5. Redis still says 28776510: a stale read, until the key expires.
6. Fix: the code that commits a transfer also deletes the cached key. GET bal:1100000001 -> ''
   The next read misses and reloads the true balance. A balance shown on a screen can be
   briefly stale; the check before spending must always read PostgreSQL (Portfolio 3).
